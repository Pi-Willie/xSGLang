# Overnight research session — Branch-GRPO on Qwen3-4B (H100)

## Mission

You are running an autonomous ML research session. The objective is to produce the **best
possible Branch-GRPO-trained Qwen3-4B math model**, together with a complete and honest
research record. Treat this as research, not a one-shot script: form hypotheses, run
controlled experiments, characterize noise, make decisions from evidence, and write down
what you did and why. Work continuously until the Completion Contract (§9) is fully
satisfied, then cleanly shut down and sync.

## Priority order (use this whenever you trade off)

1. **Loop health, timing, and verified weight movement.** Prove the machine actually works —
   weights move, generations change after refresh, no leaks, parity holds, throughput is
   measured — *before* trusting any reward number.
2. **Stable, real training signal.**
3. **Reward shaping and hyperparameter quality.**

Be efficient with H100 time, but when establishing correctness, patience beats speed.

## Hard constraints

- **Branch-GRPO only.** Do NOT implement, run, or compare against flat/normal GRPO. All
  effort goes into making Branch-GRPO work and proving it works well.
- **`plan.txt` in the repo is the authoritative algorithm spec.** Read it first and implement
  exactly that (fixed 4×2×2×2 tree, leave-one-out sibling advantage, constant
  generation-budget denominator with no length/std normalization, edge multiplicity via
  leaf-slot materialization, one accumulated optimizer step per update, xsglang for
  rollout/fork/KV and in-memory weight refresh, logprob parity gating, FP32 master weights).
  If you deviate, log the reason in the notebook.
- **The H100 is PREEMPTIBLE.** Assume the machine can disappear at any moment. The preemption
  protocol (§8) is always in force.
- This is autonomous and overnight: never block waiting for human input. Make reasonable,
  documented choices and keep moving.

## Phase 1 — Data

**A. RL prompt + eval set — OpenR1-Math-220k, streamed.**
- Stream `open-r1/OpenR1-Math-220k` with `datasets` `streaming=True` (do not download the
  whole thing). Authenticate to HF if needed.
- Inspect the schema. Keep only `(problem, answer)`. Normalize the ground-truth answer (strip
  whitespace, `$`, `\boxed{}`, etc.). **Keep a row iff the normalized answer is non-empty and
  ≤ 5 characters.** Skip everything else. Rationale: the model should not have to learn
  complex LaTeX formatting — short answers keep the verifier clean.
- Materialize a filtered RL prompt pool **and a fixed held-out eval split that is never
  trained on**. Record counts. Save to disk and sync.

**B. SFT format set — `math-fireworks.jsonl`.**
- Inspect its schema. Map each row to the exact target schema:
  ```
  <think>{reasoning}</think>
  <answer>{answer}</answer>
  ```
  (a single newline between `</think>` and `<answer>`).
- Build the SFT dataset: prompt = the problem under whatever prompt template you will also use
  at RL time; completion = the schema string. **The prompt template must be identical between
  SFT and RL.**

## Phase 3 — Implement Branch-GRPO

- Implement exactly the algorithm in `plan.txt`. xsglang does rollout / fork / KV reuse and
  in-memory weight refresh; the trainer does exact autograd via leaf-slot materialization.
- **Verifier:** extract the content of `<answer>…</answer>`, normalize, string-compare to the
  ground truth → binary reward (1/0). Missing or unparseable answer → reward 0. No LLM judge,
  no partial credit in v1.

## Phase 4 — Prove the loop is healthy (before chasing reward)

Run the `plan.txt` smoke config and assert, with logged evidence in `LAB_NOTEBOOK.md`:
- xsglang↔trainer **logprob parity** within `plan.txt` thresholds.
- The loss **denominator is the constant** `P·Bmax·Tmax` on every update.
- After an optimizer step + weight refresh, **trainer weights actually moved** (weight-delta
  norm > 0) **and xsglang generations actually changed** (log a concrete before/after diff).
- **No KV / memory leak** across many updates (flat GPU memory).
- Zero-advantage prompts contribute zero gradient; mixed-sibling nodes contribute nonzero.
- Per-phase timing logged: rollout and train tokens/s, branch-spawn ms, weight-refresh
  seconds, peak memory.

If any check fails, **stop and fix it** before continuing. Priority #1 is a healthy, fast
loop with verified weight movement.

**Gate:** all health checks green and recorded.

## Phase 5 — Characterize noise (so "improvement" is meaningful)

- Before scaling, estimate evaluation noise: run the held-out greedy eval several times and/or
  across a few seeds, and compute the metric's std (or a bootstrap CI over the eval set).
  Record this **noise band**.
- Define, and then use everywhere: **real improvement = a gain that exceeds ~2σ of the noise
  band and is sustained over multiple consecutive eval points** — not a single lucky eval, not
  within-variance wiggle.

---

## Phase 6 — Train, iterate, saturate

- Move to the main `plan.txt` config and scale sensibly. Train Branch-GRPO and iterate like a
  researcher: tune reward shaping, branch behavior, wave/batch sizes, and LR within the
  spec's spirit — **changing one thing at a time** and attributing each effect.
- Watch the load-bearing diagnostics from `plan.txt` (sibling-disagreement / mixed-node rate
  and mean|advantage| by depth, grad-norm, approx-KL, entropy, response length, reward) plus
  held-out greedy accuracy and pass@k.
- **Keep training while held-out accuracy shows real improvement (§5). Continue until it
  PLATEAUS** — no noise-exceeding improvement over a defined window of consecutive eval points
  = RL saturated. Then stop. Do not stop on a noisy dip; do not keep burning compute on a flat
  curve.
- Continuously checkpoint the **best-by-held-out-eval** model and pull it local whenever it
  improves.

---

## Phase 7 — Taste test

- Periodically and at the end, qualitatively inspect the best model on held-out prompts:
  format adherence, think/answer coherence, and absence of degeneration (repetition, empty
  `<think>`, gibberish, mode collapse, answer-hacking such as always emitting a frequent
  answer). Compare against the SFT starting point.
- Make an explicit call: **is the branch model sound or broken?** If broken, diagnose, roll
  back to the last good checkpoint, fix, and continue. Record the verdict and the evidence.

---

## Phase 8 — Preemption protocol (always on)

- After every code change: `git commit` + push.
- Checkpoint frequently to durable storage: model + optimizer + RL state + RNG + a
  phase/state file. Mirror the critical artifacts to the local workstation (SFT base, current
  best Branch-GRPO model, configs, `LAB_NOTEBOOK.md`, all curves/metrics).
- **Resume must be idempotent:** on startup, read the state file, find the last good
  checkpoint, and continue exactly from there. Never restart from scratch when a valid
  checkpoint exists.
- Treat losing the machine as expected, not exceptional.
